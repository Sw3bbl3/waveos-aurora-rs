# The display core (`kernel/src/drivers/gpu/`)

For engineers writing display or GPU drivers (Intel, AMD, Nvidia, virtio-gpu 3D) and working on the DRM device node. The code is the reference; this note gives the shape of it and the plan.

## Object model

Every display driver implements `KmsDevice` (`gpu/mod.rs`) and exposes the objects Linux KMS has, with ids (`ObjId`, unique across devices, never 0):

| Object | Type | What it is |
|---|---|---|
| CRTC | `CrtcInfo`, state `CrtcState` | A scanout engine: active or not, a `Mode`, the connectors it drives |
| Plane | `PlaneInfo` (`Primary`, `Cursor`, `Overlay`), state `PlaneState` | Feeds a CRTC from a framebuffer: `src` rectangle in 16.16 fixed point, `dst` on the CRTC, cursor hot spot |
| Encoder | `EncoderInfo` | Links CRTCs (`possible_crtcs` mask) to connectors; bookkeeping for now |
| Connector | `ConnectorInfo` | Kind (HDMI-A, DP, eDP, Virtual…), status, modes (preferred first), raw EDID, size in mm |
| Buffer object | `bo::BufferObject` (`Arc`) | Pixel memory: system RAM in physically contiguous runs, mapped once into the kernel; `chunks()` is the DMA scatter list. A driver binds its own object to it (`bind`, e.g. a virtio resource id) and is told on the last drop (`Unbind`) before the memory is freed |
| Framebuffer | `bo::Framebuffer` (`Arc`) | A buffer object viewed as an image: width, height, pitch, offset, DRM fourcc |
| Mode | `mode::Mode` | Field-for-field DRM's `drm_mode_modeinfo` (timings, clock, flags, type) |

`Caps` says what the device can do: live mode changes, any size (virtual displays), whether `dirty` is needed, cursor plane size, vblank interrupts, whether the preferred mode follows a host window.

EDID is parsed by `libs/edid` (`aurora-edid`, host-tested with `cargo test -p aurora-edid`): base block (identity, size, established, standard and detailed timings, name, range limits), CTA-861 (detailed timings, short video descriptors with a VIC table, HDMI VSDB) and DisplayID type I timings. Standard timings are completed with CVT reduced blanking (`aurora_edid::cvt_rb`); for real panels a DMT table lookup should come first (DMT and CVT differ for some sizes).

## State changes: atomic commits

`KmsDevice::atomic_commit(&Commit)` takes the CRTCs and planes that change, all or nothing, with DRM's flag values (`TEST_ONLY`, `ALLOW_MODESET`, `PAGE_FLIP_EVENT`, `NONBLOCK`). `gpu::validate` merges a request into the committed state and checks the shared rules (objects exist, planes go to CRTCs they can feed, sources inside framebuffers, a primary plane covers its CRTC unscaled, cursor fits the plane, active CRTCs have a mode and a connector, a mode change needs `ALLOW_MODESET`). Drivers call it, then add their own limits in `atomic_check`.

- **Page flips without copies.** Putting a different framebuffer on a primary plane is a flip. On virtio-gpu the buffer's memory is the host resource's backing, so a client buffer can be scanned out directly once it is wrapped in a `Framebuffer`.
- **Damage.** `dirty(fb, rects)` (DRM's DIRTYFB) shows changed rectangles of a framebuffer wherever it is scanned out. Devices that scan out of VRAM (GOP, Bochs) copy the rectangles there; virtio-gpu transfers and flushes them.
- **Events.** `gpu::post(Event::Flip { crtc, seq, time_ns, user_data })` after a commit with `PAGE_FLIP_EVENT`; `Event::Hotplug` from `gpu::hotplug()`. `KmsDevice::vblank(crtc)` is the frame counter and timestamp. Devices without vblank interrupts (virtio-gpu) count a frame when the device has taken the picture. Commits are synchronous today; `NONBLOCK` is accepted and ignored.
- **Sleep.** `resume()` restores the committed state; `gpu::resume_all()` runs from `drivers::resume`.
- **Backlight.** A driver that controls the internal panel's backlight registers a `gpu::Backlight` with `gpu::set_backlight`; `gpu::brightness()`/`set_brightness()` (0–100) are what the brightness keys use.
- **Contiguous buffers.** `BufferObject::alloc_contiguous` gives one physical run (or `None`); drivers that scan out of RAM use it for screen-sized dumb buffers so `panic_framebuffer` can point at them.

## Drivers today

| Driver | File | Notes |
|---|---|---|

| Bochs/QEMU std VGA | `bochs.rs` | DISPI registers, any listed mode at run time |
| Ported Linux virtio-gpu | `linux.rs` | Only with `gpu=linux` in boot.conf (`cargo xtask run --gpu virtio-linux`) |
| Native virtio-gpu | `virtio/` | Default for virtio GPUs |
| Intel integrated graphics | `intel/` (over `libs/igfx`) | Display 9–13; takes over the firmware's mode; see [intel-display.md](intel-display.md). Untested on real hardware |
| AMD Radeon | `amd/` (over `libs/amdgfx`) | DCE 11.2/12, DCN 1.0–3.2; takes over the firmware's mode, flips between VRAM buffers; see [amd-display.md](amd-display.md). Untested on real hardware |
| Nvidia GeForce | `nvidia.rs` (over `libs/nvgfx`) | Detection and a log line only; the firmware framebuffer stays. See [nvidia-display.md](nvidia-display.md) |

The three simple ones share `simple.rs` (one CRTC, one primary plane, one connector; the backend sets modes and shows rectangles).

**virtio-gpu** is split so 3D can reuse the bottom half:

- `virtio/proto.rs`: the wire format, 2D and 3D command codes, the control header (with context id and ring index).
- `virtio/cmd.rs`: `Gpu`, the command layer. A pool of request/response slots on the control queue, `submit` (batchable, optional extra read-only buffer), `wait`, fences (`Cmd::set_fence`, `fence_done`, `wait_fence`), resource ids, the cursor queue, reset after sleep. Nothing display-specific.
- `virtio/mod.rs`: the KMS device. One head per scanout (CRTC, primary and cursor plane, encoder, Virtual connector with EDID). A framebuffer's buffer object becomes a `RESOURCE_CREATE_2D` + `ATTACH_BACKING` resource on first use; `dirty` sends one transfer and one flush per rectangle, notifies once and waits once; the cursor plane uses `UPDATE_CURSOR`/`MOVE_CURSOR`. A `virtio-gpu` task reads `EVENT_DISPLAY` (the MSI-X handler flags it), probes again and reports hotplug.

A virgl/Venus implementation adds context commands (`CTX_CREATE`, `SUBMIT_3D`, blob resources) through `Gpu::submit` with `Header::ctx`, and fences through `wait_fence`; it needs a per-context ring index and asynchronous fence completion (a reaper task woken by the interrupt) rather than the synchronous waits 2D uses.

## The compositor's side

Lumen Server uses `output::Output`: a connector, its CRTC, primary and cursor planes. `Output::open_all` opens every connected connector of every device (the primary device's first), each on a CRTC of its own (chosen by `possible_crtcs`, skipping those taken); `Output::open_connector` opens one (hotplug); `Output::disable` switches one off. The back buffer the compositor draws into *is* the primary plane's framebuffer, so presenting is `dirty` on the damaged rectangles: on virtio-gpu there is no copy in the guest at all. Resolution changes (Settings, "Keep this resolution?", following a host window via `follow_preferred`) are new framebuffers committed with `ALLOW_MODESET`. The pointer goes on the cursor plane when there is one (`cursor=software` in boot.conf turns that off); shapes too large for a 64×64 plane at 2× are drawn into the picture for as long as they are shown.

Its commits and presents go through `gpu::owner` (`desktop_commit`, `desktop_dirty`), which keeps them aside while a Linux program drives the display (see [Who drives the display](#who-drives-the-display)); anything else that shows the desktop should do the same.

Timing: the compositor's "time by stage" line counts the present as `flush`, and a `present on <driver> <connector>` line every 10 seconds gives each display's frames, mean and max cost, pixels per frame, frames it held back while busy and frames scanned out directly; `compositor busy` gives the share of those 10 seconds the compositor spent in its frames. The line per frame (`frame: full|partial|cursor, pixels, ms, displays`) is written only with `frame_log=1` in `boot.conf`: every byte of the log is port I/O on the serial line, slow under emulation, and it went out on every frame (the benchmark scripts that read those lines need the option).

### Programs' buffers, composited where they are

A client window shows either its own surface (shared memory the kernel allocated: `win_surface`, drawn, `win_present`) or a buffer of its program's, attached as it is (`win_buffer`, `win_attach`; Linux programs only, through `wl-bridge`): a dma-buf, or pages of a shared memory object (`memfd`, `/dev/shm`). `win_buffer` makes a `gui::server::WinBuffer` over the descriptor's memory — a dma-buf's own `BufferObject`, or a `BufferObject::from_shared` that holds each shared-memory frame (`vmm::shm_hold_all`) and maps them into the kernel once — with offset, size, stride and format (`XRGB8888`, or premultiplied `ARGB8888`, Wayland's). The compositor reads it in `ClientApp::draw` (`server::with_content`, `Canvas::blit_buffer`: rows of any stride, XRGB's top byte made opaque, ARGB over white as the bridge composed it) — the only copy between the program's renderer and the display, and none at all when the display scans the buffer out.

Lifetime: the window holds the buffer it shows (an `Arc`), a display scanning one out holds it in its framebuffer, and the program's buffer object or shared memory frames stay until the last holder goes, so a program that exits, is killed or unmaps its memory mid-frame leaves nothing dangling. Reading happens under the client lock, which `win_attach` takes too: the buffer a new attach replaces is no longer read, and the program hears `event::BUFFER_RELEASE` for it at once — unless a plane shows it, in which case it is released when the display has flipped away (`server::set_on_plane`). A buffer never composited before the next attach is simply released (that frame is dropped). Damage is in buffer pixels, turned into points by the attach's scale; a buffer drawn for another scale than the display's is scaled (nearest pixel) until the program catches up.

### Direct scanout

`Desktop::scanout_window(area)` names the client window whose content alone is what a display shows: a full-screen window (`win_set_fullscreen`; `wl-bridge` for `xdg_toplevel.set_fullscreen`) covering the display, or the program in front in Wave Play — with nothing of the desktop over it (no Shoal, menu, Drift, Spotlight, switcher, Current, drag, tour, reveal, Crest notice, Wave Play overlay or toast) and the pointer on the cursor plane, or not drawn on that display (hidden by the program, or elsewhere). When that window shows an attached buffer of the display's pixel size without alpha (`XRGB8888`), `Screen::scan` wraps it in a `Framebuffer` (`Framebuffer::with_offset`, made once per buffer and kept while the buffer lives) and puts it on the primary plane with a desktop commit (`Output::scan_out`, through `gpu::owner`): a page flip, and nothing is composed for that display while it lasts. A new buffer is another flip; the same buffer attached again with new pixels is a `dirty` of its framebuffer. When the conditions stop holding — a notice, a menu, the pointer shown again without a cursor plane, the window leaving full screen, closing or its program dying — the display's back buffer is painted in full that frame and flipped back (`Output::scan_back`), and the buffer goes back to its program. A device that can't scan a buffer out (virtio-gpu needs rows exactly `width × 4` bytes apart, from the start of the buffer) refuses the commit, and that buffer is composited instead.

### Frame timing

A window's `FRAME` event says when its picture is shown: the start of the display's next frame (`Output::frame_clock`: the device's vblank counter when it has interrupts, otherwise the steady clock at the mode's refresh rate that the DRM device gives programs), with that frame's number, its time (`CLOCK_MONOTONIC` nanoseconds), the refresh period and flags (`aurora_abi::frame`: vsync, hardware clock, zero copy when scanned out). It goes as soon as the picture was composed or flipped — the program draws its next one while this one waits for the frame start — but no more than one per display frame: a window that already had one in the current frame gets the next at the next frame start (the compositor wakes for it). `wl-bridge` answers frame callbacks and `wp_presentation` feedback with it, so programs that draw on each callback (Mesa's EGL with swap interval 1) run at most at the refresh rate, with presentation times on frame starts. (Waiting for the frame start before every event was tried first: with Mesa's `kms_swrast`, which rasterises a frame only once the previous callback came, that made every frame wait half a refresh on average for nothing.)

## Several displays

`gui/screens.rs` (the compositor) and `gui/desktop/displays.rs` (the desktop) build on the outputs; the arrangement math is `lumen::displays` (host-tested: `cargo test -p lumen displays`).

- **One space of points.** Every display is a rectangle in one global coordinate space, in points; the main display (menu bar, Harbor, Shoal, Spotlight, notifications, Shore and Wave Play) is at (0, 0) and is the desktop's own `w`×`h`, so everything that was laid out for "the screen" stays on it. The others touch it or each other along an edge (`displays::arrange`, `snap`): no overlaps, no islands. Damage is in global points; each display paints the part that falls on it with a `Canvas` over its own back buffer, at its own scale, whose `origin` is the display's corner (`Canvas::with_origin`).
- **Per display:** mode, scale (its own choice, else the system's, else 2× from 2560×1440), back buffer, wallpaper, the desktop's reusable pictures (scene, drag backdrop: swapped in while that display is painted), material cache, cursor plane and damage. A client window's surface is drawn at the scale of the display it is on: moving to a display with another scale sends `RESIZE` with the new scale, and until the client catches up its old surface is drawn scaled.
- **Presenting.** With one display the present happens right after painting, as before. With several, each display presents from a task of its own (`Presenter`); a display still taking its last picture is not painted — its damage waits (`deferred`) and is painted in full once it is idle — so a slow or stuck display holds up only itself. Mirroring paints the main display only and copies its new pixels to the others (switched to the main display's resolution when they can, and back afterwards).
- **The pointer** crosses between displays where they touch and stops at the outer edges (`displays::constrain`); the cursor plane of the display it is on shows it, the others hide theirs. Input devices count from (0, 0) at the top left of the rectangle around all displays; `input::warp` keeps relative devices in step when the pointer is stopped. (A QEMU USB tablet is absolute over that whole rectangle, not per window.)
- **Hotplug** (`gpu::hotplug`, a host window resized) and preference changes run `Compositor::reconfigure`: displays that went away are switched off (`Output::disable`), new ones opened in their saved resolution, then everything is laid out again and handed to the desktop (`Desktop::set_displays`). Windows move with their display; a removed display's windows go to the main display remembering where they were (`displays::migrate`), and return when the same display (by identity) comes back, unless moved by hand meanwhile.
- **Preferences.** Each display's place, resolution, scale and wallpaper are one preference, `display_<identity hash>` = `x,y,width,height,scale,wallpaper` (`displays::Record`), plus `display_primary` and `display_mirror`. The identity hashes the EDID's maker, product, serial number and name with the connector name, so a monitor gets its arrangement back on any boot. Settings → Display edits them (drag the displays, or put one beside the main display; main display; mirroring; each display's resolution, scale and wallpaper).
- **For apps:** `desktop::DISPLAYS` (a `DisplayInfo` per display, the main one first), `desktop::WINDOW_DISPLAY` and `desktop::DISPLAY_MODES` (no new system call numbers: requests of the `desktop` call), and the `event::DISPLAY` event when a window changes display or the displays change; `corekit::display`, `aurorakit::App::display_changed` and `waveui::Env::display` wrap them. Programs that don't ask see the main display, as before (`SCREEN`, `sys_info`).

Interfaces added to the core for this (all additive): `Output::open_all`, `Output::open_connector`, `Output::disable`, `Output::framebuffer`, `Output::connector_info`. Nothing in `KmsDevice` or the object model changed.

## The DRM device (`/dev/dri/card0`)

Linux programs reach the display core through the DRM uAPI (and Debian's Mesa runs on it unmodified: see [Mesa](#mesa)), in the Linux compatibility layer (`kernel/src/compat/linux/drm/`): Linux's ioctl numbers and struct layouts, copied in and out by the size encoded in each ioctl number and zero-extended (so programs built against older or newer headers work), and Linux's error codes. `linux-tests/drmtest.c` writes the structs out by hand and checks their sizes against Linux's.

**Nodes and enumeration.** `card<N>` is `gpu::devices()[N]` (char 226:N). `/sys/class/drm/card0` and `/sys/dev/char/226:0` link to `/sys/devices/pci0000:00/<slot>/drm/card0` (`dev`, a `uevent` with `DEVNAME=dri/card0`, connector folders with `status`, `modes`, `edid`…); the PCI device has `vendor`, `device`, `subsystem_*`, `revision`, `class`, `config` and a `uevent` with `PCI_SLOT_NAME`, and its `subsystem` links to `/sys/bus/pci` (`compat/linux/sysfs.rs`). That is everything libdrm's `drmGetDevices2`, `drmGetDevice2`, `drmGetDeviceNameFromFd2` and `drmGetMinorNameForFD` read. Every card is presented as a PCI device (the firmware framebuffer as the boot VGA's), because libdrm cannot enumerate a platform device without device-tree properties.

**Driver identity.** `DRM_IOCTL_VERSION` gives the name Linux's driver for the same hardware has — `virtio_gpu`, `bochs-drm`, `simpledrm` — since Mesa picks its user-space driver by it (with no 3D, Mesa's virgl fails to start and GBM falls back to `kms_swrast`). A hardware driver implements `drm::Driver`: name, description, date, version, `render()` (a render node `renderD<128+N>` is offered when true) and `ioctl()` for its private range `0x40`–`0x9F` (argument copied in and out like the core ones). Core ioctls not allowed on render nodes are refused there with `EACCES`.

| Group | ioctls | Notes |
|---|---|---|
| Core | `VERSION`, `GET_UNIQUE`, `SET_VERSION`, `GET_CAP`, `SET_CLIENT_CAP`, `GET_MAGIC`, `AUTH_MAGIC`, `SET_MASTER`, `DROP_MASTER`, `MODESET_CTL` | `GET_UNIQUE` is empty until a master asks for interface 1.1, then `pci:0000:00:02.0` (libdrm's `drmOpenByName` depends on that). Caps: dumb buffers, PRIME import+export, monotonic timestamps, CRTC in vblank events, cursor size, `ADDFB2` modifiers (linear); no syncobjs, async flips or flip targets. Client caps: stereo, universal planes, atomic (implies universal planes), aspect ratio, writeback and cursor hotspot (both need atomic). |

| Properties | `OBJ_GETPROPERTIES`, `GETPROPERTY`, `GETPROPBLOB`, `CREATEPROPBLOB`, `DESTROYPROPBLOB`, `OBJ_SETPROPERTY`, `SETPROPERTY` | Plane `type`, `FB_ID`, `CRTC_ID`, `SRC_*`, `CRTC_*`, `IN_FORMATS` (the plane's formats, each with the linear modifier), `HOTSPOT_X/Y` (cursor planes, with the hotspot cap); CRTC `ACTIVE`, `MODE_ID`; connector `EDID`, `DPMS`, `CRTC_ID`, `link-status`, `non-desktop`. A blocking commit returns once its frame is on screen; a nonblocking one, and `PAGE_FLIP`, fail with `EBUSY` while the CRTC's previous flip is pending. |
| Buffers | `CREATE_DUMB`, `MAP_DUMB`, `DESTROY_DUMB`, `ADDFB`, `ADDFB2`, `RMFB`, `CLOSEFB`, `GETFB`, `GETFB2`, `GEM_CLOSE` | A file's handle table holds `Arc<BufferObject>`s (32-bit dumb buffers come from the device's `create_dumb`). `MAP_DUMB` gives `buffer id << 32` as the `mmap` offset; the mapping holds the buffer's frames (`BufferObject::user_frames` counts them like shared memory), so they outlive the handle and the buffer. Formats are what some plane takes (XRGB8888, ARGB8888), linear: `ADDFB2` takes `DRM_MODE_FB_MODIFIERS` with `DRM_FORMAT_MOD_LINEAR` and refuses other modifiers, and `GETFB2` reports the flag and modifier. Framebuffer ids are global, as on Linux: a master may show the desktop's framebuffer it read at start (programs restore the CRTC they found when they end). `RMFB` of a framebuffer on screen turns its planes (and, for a primary, the CRTC) off, as Linux does. |
| PRIME | `PRIME_HANDLE_TO_FD`, `PRIME_FD_TO_HANDLE` | A dma-buf is a descriptor holding the buffer object: it passes over `SCM_RIGHTS`, maps with `mmap` from offset 0, tells its size with `lseek(SEEK_END)`, takes `DMA_BUF_IOCTL_SYNC`; importing gives the handle the buffer already has in that file. Its implicit fences are always signalled (everything renders and scans out synchronously today): `poll` says readable and writable, `DMA_BUF_IOCTL_EXPORT_SYNC_FILE` gives a signalled sync file (`poll`, `SYNC_IOC_FILE_INFO`, `SYNC_IOC_MERGE`), `IMPORT_SYNC_FILE` takes one. A window can show it as it is (`win_buffer`, see [Programs' buffers](#programs-buffers-composited-where-they-are)). |
| Vblank | `WAIT_VBLANK`, `CRTC_GET_SEQUENCE`, `CRTC_QUEUE_SEQUENCE` | See below. |

**Vblank and events.** Devices with vblank interrupts count frames themselves (`KmsDevice::vblank`, `Caps::vblank_irq`). The others get a steady clock per CRTC at its mode's refresh rate (frame *n* begins *n* periods after boot), and a flip completes at the next frame: a program flipping on each event runs at the refresh rate, as on Linux. Events (`FLIP_COMPLETE`, `VBLANK`, `CRTC_SEQUENCE`; at most 4 KiB per file) wait in the file until due; a timer wakes `poll`, `epoll` and blocking `read`s then, and `read` returns whole events only. The DRM layer makes the flip events itself after the (synchronous) commit and does not pass `PAGE_FLIP_EVENT` to drivers; a driver whose commits become asynchronous must report completion to it instead.

### Who drives the display

The first program to open a card while nobody is master becomes master, as on Linux; `SET_MASTER` takes master when it is free (WaveOS has no seat manager: the person at the computer owns its display, so no privilege is needed) and `DROP_MASTER` gives it up. Opening the card, reading state, making buffers and testing commits take nothing from the desktop. The master's first real change — a mode set, plane, cursor, page flip or atomic commit — **takes the display** (`gpu::owner::client_commit`):

- The desktop's state (every CRTC and plane) is kept aside, and its cursor and overlay planes are turned off in the same commit.
- While the program holds the device, `Output`'s commits go through `owner::desktop_commit` and change only the kept state (checked by the core's rules all the same), and its presents (`owner::desktop_dirty`) reach nothing. Lumen Server goes on drawing into its back buffer.
- When the master drops master, or its file closes — the program exited, crashed or was killed, since a process's descriptors are closed when it is cleaned up — `owner::give_back` commits the kept state again with `ALLOW_MODESET` (from a blank state if that fails) and shows the desktop's framebuffers in full. The desktop is back without the compositor doing anything.

Input still goes to the desktop while a program holds the display (evdev is separate work), and nothing but the program's end gives the display back; a key that revokes master (as a VT switch does on Linux) is a follow-up. With several programs, master passes between them without the desktop in between: the kept state stays the desktop's.

### Mesa

Debian 12's Mesa 22.3 runs unmodified on the card, through its software path: GBM and EGL on `card0` load `kms_swrast`, llvmpipe (Mesa's LLVM JIT rasteriser) draws into dumb buffers, and the frames are shown with `ADDFB2` and page flips with events. That gives OpenGL ES 3.2 and desktop OpenGL 4.5 full screen, Vulkan 1.3 through lavapipe, and GL in a WaveOS window through the Wayland bridge. It is the whole user-space stack (libdrm, GBM, EGL, the GL dispatch, the Vulkan loader and WSI) that hardware drivers will reuse; only the driver at the bottom changes.

- **Driver selection.** On virtio-gpu Mesa first tries virgl, which asks `DRM_IOCTL_VIRTGPU_GETPARAM` (driver-private: `EINVAL` here) and gives up; GBM then falls back to `kms_swrast` (`GBM_ALWAYS_SOFTWARE=1` or `LIBGL_ALWAYS_SOFTWARE=1` skips the attempt). On `bochs-drm` and `simpledrm` no hardware driver exists and the fallback is immediate.
- **What the kernel gives it.** Dumb buffers mapped through the card: `kms_swrast` maps the back buffer for each frame and unmaps it after, so `mmap` and `munmap` of a 4 MiB buffer run once per frame (both take the shared-frame counts' lock once per call, not once per page, and skip TLB flushes for pages that weren't mapped). Planes list their formats with the linear modifier in `IN_FORMATS`; `ADDFB2` takes `DRM_MODE_FB_MODIFIERS` with `DRM_FORMAT_MOD_LINEAR` (and refuses others, `MOD_INVALID` included, as Linux does) and `GETFB2` reports it. `mincore` (EGL tells a Wayland display from other native displays with it), `close_range`, `sched_setscheduler` (Mesa's worker threads ask for `SCHED_IDLE`), `/proc/cpuinfo` with `cpuid`'s flags (only those the kernel enables: AVX, not AVX-512) and `/sys/devices/system/cpu` (glibc counts processors there; LLVM picks its code generation by `cpuid`, which is why `cargo xtask run` presents an emulated processor as a Haswell). The udev record `/run/udev/data/c226:N` (kept with the input devices' records, in `compat/linux/input`'s tree), without which libudev's enumerators count a card as not set up yet: glmark2 finds the card through libudev this way. A program may put back the desktop's framebuffer it read at start (glmark2 restores the CRTC on exit); the desktop gets the display back when it closes the card either way. `GETFB`/`GETFB2` give a master a handle to a framebuffer it didn't make (so it could map the screen's pixels) only with the sandbox's `screen-capture` ([sandboxing.md](sandboxing.md)); putting it back by id needs no handle. Bochs marks the firmware's mode preferred: programs that pick "the preferred mode" took the largest, 3840×2400, before. The simple displays (Bochs, the firmware framebuffer) take ARGB8888 on their primary plane too, shown as XRGB8888: EGL configs with alpha (glmark2's) ask for it.
- **Measuring.** When a card that showed frames closes, the system log gets a line per program: frames, frames per second, and per frame the time it spent drawing (from its previous frame being shown to its next commit), the commit's time in the kernel, and the wait until the frame was on screen (`drm: kmscube on card0: 241 frames in 6952 ms (34.6 per second); per frame: drawing 18.70 ms, commit 0.47 ms (max 2.42), until shown 9.74 ms`). `WAVEOS_SYSCOUNT=1` in a program's environment writes its system calls' counts and times to the log when it ends; `tools/sample_vcpus.py` samples where QEMU's virtual processors are (user code, idle, which kernel function).

#### Mesa performance

Measured in QEMU emulating the processor (TCG, 4 virtual processors, on the 8-core build Mac shared with other work), 1280×800 at 60 Hz, kmscube's 240 frames in `cargo xtask test --mesa`. TCG timings swing by half or more between runs of the same build (the host's other load), so the numbers below are ranges over runs, and the before/after comparison was made inside one boot.

- **Frame rate.** kmscube reports 25 to 52 frames per second, 30 in most runs, on virtio-gpu and Bochs alike (the per-card summary 23 to 38: it counts from the first mode set): drawing a frame takes 19 to 33 ms, mostly longer than one 16.7 ms refresh, so most frames are shown at every second frame start. The commit is 0.5 to 2 ms (virtio-gpu: setting the scanout and one transfer and flush of the whole frame; Bochs: copying it into video memory), and the wait until the next frame starts 7 to 12 ms. A frame drawn in under 16.7 ms would run at 60.
- **Where the time goes.** Sampling the virtual processors while kmscube runs (`tools/sample_vcpus.py`, 1020 samples): 55% idle, 34% in user code (llvmpipe's JIT-compiled shaders and rasteriser, Mesa, the C library), 11% in the kernel: interrupt entry 3%, programming the local APIC timer 2.5% and its end-of-interrupt 2.5% (memory-mapped registers QEMU emulates slowly; cheap on hardware), inter-processor interrupts 1%, shared mappings 1%, futexes under 1%. llvmpipe's threads wait for each other and for the frame, so the processors idle half the time even while the cube spins. Per frame, kmscube makes about 43 futex calls, maps and unmaps its 4 MiB back buffer once (`kms_swrast` does), two ioctls (`MAP_DUMB`, `PAGE_FLIP`), one `pselect` and one `read` of the flip event (`WAVEOS_SYSCOUNT=1`).
- **What changed.** Mapping and unmapping the back buffer took 1 to 2.6 ms and 0.5 to 0.7 ms per frame in kmscube. The shared-frame counts are now taken and given back under one lock per call rather than one per page, and fresh pages get no TLB flush. Measured interleaved in one boot (30 rounds of each, medians, two boots): mapping a 4 MiB buffer went from 263 to 205 µs and from 324 to 209 µs, unmapping from 361 to 214 µs and from 424 to 279 µs. In kmscube itself the difference is within TCG's noise. Flip events now arrive at the frame's start to the nanosecond rather than up to a millisecond after. On Bochs, kmscube had taken the largest mode, 3840×2400 (nine times the pixels), for lack of a preferred one: 5 to 7 frames per second there, now 30 at 1280×800, as on virtio-gpu.
- **glmark2** chooses the largest mode, 3840×2400 here, as on Linux: its `build` scene runs at 4 to 7 frames per second and `texture` at 2 to 3. **es2gears** in a 300×300 window through the bridge shows a frame about every 25 ms; since the frames reach the window without copies and frame callbacks follow the display, it runs at the refresh rate (59 frames a second, see [Measurements](#measurements)). **vkcheck** creates its Vulkan device and pipeline and draws in 1 to 2.3 seconds, most of it lavapipe compiling the shaders on the first draw.
- **Next.** The shared-frame counts are a `BTreeMap` with an entry for every page of every mapped library (LLVM alone is 100 MiB), so each page of a shared mapping costs a tree lookup; a count per physical frame (an array, as Linux's `struct page`) would make it constant. Beyond the kernel, the frame time is llvmpipe's, and on hardware with virtualization (KVM, HVF) or with a GPU driver it changes entirely; measuring there is the next step.

#### Mesa in a window

GL and Vulkan reach WaveOS windows through `wl-bridge`, and since this work without copies between the program's renderer and the compositor:

1. **Which driver.** `/etc/drirc` in the system image (`linux-programs/mesa/drirc`) names `kms_swrast` as the driver for `virtio_gpu`, `bochs-drm` and `simpledrm` (Mesa's loader reads `dri_driver` from driconf for the kernel driver it finds). GBM then loads it at once instead of trying virgl first, and Mesa's EGL Wayland platform, which before fell back to software drawing into `wl_shm`, renders with llvmpipe into dumb buffers on `card0`. The browsers are left out (`voyage`, `WebKitWebProcess`, `firefox-esr`: an empty `dri_driver`, Mesa's own choice): given a GL device on Wayland, WebKit and GTK draw their whole window with GL, which on llvmpipe was a third as fast while scrolling as their own drawing into shared memory — which WaveOS now shows without a copy too. (Remove the `virtio_gpu` entry when virtio-gpu 3D comes.)
2. **linux-dmabuf and wl_drm in the bridge.** `wl-bridge` offers `zwp_linux_dmabuf_v1` version 4 (default and per-surface feedback: a format table with XRGB8888 and ARGB8888, each linear and with the implicit modifier, `main_device` and the tranche's target device `226:0`; the format and modifier events below version 4; `create_params`, `add` (one plane), `create` and `create_immed`) and Mesa's `wl_drm` version 2 (`device` `/dev/dri/card0`, formats, the PRIME capability, `authenticate`, `create_prime_buffer`). Mesa 22.3 needs `wl_drm`: it takes the device from the dma-buf feedback only when the device has a render node. The buffers arrive as dma-bufs.
3. **Attached as they are.** The bridge doesn't copy what a window's surfaces commit — its main surface, sub-surfaces (Firefox draws its page in one; videos come in another, often through a viewport) and pop-up menus: it makes a WaveOS buffer over each buffer once (`win_buffer`) and attaches them (`win_attach`): one alone when it is all the window shows (a display may then scan it out), otherwise as layers (`attach::LAYERS`, `WinLayer`s bottom first, each a source rectangle of its buffer at a place in the window, scaled when the viewport says so; the window geometry's crop of GTK's shadows is just a layer placed partly outside). It answers `wl_buffer.release` when WaveOS sends `BUFFER_RELEASE` (a buffer left out of the next attach is released). Shared memory (`wl_shm`: GTK, WebKit, Firefox, lavapipe's Vulkan WSI, SDL) and dma-bufs take the same path. Only formats WaveOS doesn't take, more than 16 surfaces, or cursor surfaces are still composed by the bridge from copies, and a window going between the two copies or attaches on the next frame (the bridge logs which way each window goes, and why, when it changes). `WL_BRIDGE_COPY=1` in the bridge's environment turns all of this off (no dma-buf globals, every frame copied): that is the "before" of the measurements below.
4. **Damage, tight.** Browsers often say a whole surface changed when a caret blinked or a strip scrolled. The bridge compares each layer's new buffer with the one WaveOS still shows of that surface (held until WaveOS releases it, so it can't change meanwhile), row by row within the program's damage, and passes on only the rectangle that really changed, in window pixels; the window server damages just that, each display repaints and transfers only that (`dirty` rectangles to virtio-gpu, copies to Bochs's video memory). Under an opaque layer covering the whole window nothing is composed (Firefox's page over its main surface), and fully opaque rows of buffers with alpha are plain copies.
5. **Full screen.** `xdg_toplevel.set_fullscreen` becomes `win_set_fullscreen` (the configure says `fullscreen`, at the display's size); with a visual without alpha (glmark2's `--visual-config a=0`) the display scans the program's dma-bufs out directly, as above. Programs hiding the pointer (`wl_pointer.set_cursor` with no surface) hide WaveOS's over their window.
6. **Presentation.** `wp_presentation` (clock `CLOCK_MONOTONIC`): each feedback is `presented` with the time, refresh, frame number and flags of the `FRAME` event that showed the commit (`zero_copy` when scanned out), or `discarded` if the window's picture was not shown (hidden windows' callbacks are answered after 100 ms anyway). Frame callbacks are answered by the same events.

Still to do for hardware drivers: buffers from a render node (`renderD128`, then Mesa takes the device from the dma-buf feedback and `wl_drm` is not needed), tiled and compressed modifiers in the feedback's tranches and the scanout check, waiting on a buffer's fences before compositing or scanning it out (the bridge would `poll` the dma-buf or import an explicit-sync timeline, `wp_linux_drm_syncobj_v1`), and overlay planes for windows that are not full screen.

#### Measurements

`cargo xtask test --mesa` with `AURORA_MESA_BENCH=1` runs `linux_mesa_bench`: es2gears in a window, and glmark2's Wayland build (`build` and `texture`, 8 s each) in a window and full screen, each with the bridge copying as before and zero-copy, interleaved, three rounds, with the compositor running; it prints each run and the medians. Measured on virtio-gpu (QEMU TCG, 4 virtual processors, 1280×800, on the shared 8-core build Mac), three interleaved rounds, medians (each run's figures are in the log; runs of the same case differed by up to 40%):

| Case | Copied (before) | Zero-copy (after) |
|---|---|---|
| es2gears in a window, frames/s | 59 | 59 |
| … compositor busy, composing per picture | 9.2%, 1.0 ms | 13.8%, 1.7 ms |
| glmark2 (ES 2) in an 800×600 window, score | 24 | 31 |
| … compositor busy, composing per picture | 14.4%, 4.2 ms | 49.2%, 13.4 ms |
| glmark2 (ES 2) full screen, score | 16 | 23 |
| … compositor busy, composing per picture | 13.5%, 6.1 ms | 6.4%, 0.8 ms (all frames scanned out) |

Per frame, from the bridge's own lines: the hand-off (commit to the WaveOS call) is 1.2–1.4 ms for es2gears' copies and 0.2 ms zero-copy, 7.6–7.9 ms for glmark2's window copies and 0.4–0.5 ms zero-copy, 12.8–16.5 ms full screen copied and 0.4–0.5 ms scanned out; from a commit to WaveOS's `FRAME` (until shown) 5–30 ms either way. es2gears is held at the refresh rate in both (59 a second: frame callbacks are paced to the display), so its gain is the processor time the copies took; glmark2 (swap interval 0) shows it as frames. The cost that moves rather than goes: a buffer with alpha (glmark2's default visual is ARGB) was blended over white by the bridge into the window's surface and copied by the compositor; zero-copy, the compositor blends it while composing (the 13 ms above). Opaque rows of such buffers are plain copies; a window whose program declares an opaque region or uses an XRGB visual skips the blend altogether.

Browsers (`AURORA_TEST_ROOT=browsers cargo xtask test --mesa`, `linux_browsers_measured`: Voyage and Firefox on a long local page with a spinner, idle then 30 scroll notches, copies against zero-copy) were measured too, but on a host at load 60–96 their frame rates (1–11 pictures a second) swung more between identical runs than between the two modes; what the runs did show reliably: Voyage handed a GL device on Wayland drew its window with GL (dma-bufs) and composed 50–70 ms a frame with every frame a full-screen repaint, so `drirc` leaves the browsers on Mesa's own choice; Firefox's window is two layers (GTK's surface and the page's sub-surface), which before were always composed from copies.



#### What hardware drivers still need

The software path needs none of this; Mesa's hardware drivers (iris, radeonsi, nouveau/NVK, virgl/Venus) do:

- **Render nodes.** `Driver::render()` offers `renderD<128+N>`; Mesa renders through it and shows through `card0` (GBM, EGL device enumeration with `EGL_EXT_device_drm_render_node`, Vulkan's physical devices all start from it). No driver renders yet, so none is offered.
- **GEM and command submission, per vendor**, through `Driver::ioctl` (the private range): i915 (`GEM_CREATE_EXT`, `GEM_MMAP_OFFSET`, contexts and VMs, `EXECBUFFER2`) or Xe; amdgpu (`GEM_CREATE`, `GEM_VA`, `CTX`, `CS`, `INFO`; libdrm_amdgpu also reads `/sys`); nouveau (`VM_BIND`, `EXEC`); virtio-gpu 3D (`GETPARAM`, `CONTEXT_INIT`, `RESOURCE_CREATE_BLOB`, `EXECBUFFER`, `WAIT`). A file's handle table holds core buffer objects today; a driver with objects of its own adds a kind there.
- **Synchronisation.** Syncobjs (`SYNCOBJ_CREATE`/`DESTROY`/`WAIT`/`RESET`/`SIGNAL`, timelines, `HANDLE_TO_FD` and back, `TRANSFER`), real implicit fences on dma-bufs (today `poll` and `EXPORT_SYNC_FILE` say every one is signalled, which is true while everything renders and scans out synchronously), and atomic's `IN_FENCE_FD`/`OUT_FENCE_PTR`. `GET_CAP` says `SYNCOBJ` 0 until then. (kmscube's atomic mode, `-A`, needs `EGL_ANDROID_native_fence_sync`, so a hardware driver: llvmpipe has no fence descriptors.)
- **Modifiers.** A driver lists its tiled and compressed layouts per plane; `IN_FORMATS` and `ADDFB2` take them from `PlaneInfo` instead of linear only, and GBM's `gbm_bo_create_with_modifiers` then picks one.
- **Async flips** (`DRM_CAP_ASYNC_PAGE_FLIP`, tearing flips for games without vsync): glmark2 warns and falls back to mailbox presentation without it.
- **Legacy sharing.** No `GEM_FLINK`/`GEM_OPEN` (DRI2 and X servers only), no DRM leases, no gamma/CTM, no writeback connectors.
- **Input.** A full-screen KMS program needs evdev for keys and the pointer (the evdev work).
- **Vulkan on the display.** lavapipe renders and reads back; presenting full screen through `VK_KHR_display`/`VK_EXT_acquire_drm_display` (its WSI needs scanout-capable, exportable images) is untried.

## Testing

- `cargo test -p aurora-edid`: EDID base block, CTA-861, DisplayID, bad checksums, CVT.
- `cargo xtask test --gpu std|virtio|virtio-linux`: the `display: …` kernel test (connectors and EDID, two mode sets, a full and a partial present, an atomic rule, a page flip with its event, the cursor plane) and, in the sleep test, a present after waking.
- `cargo xtask test --gpu std|virtio`, the `drmtest` kernel test: `linux-tests/drmtest.c` (static, musl) enumerates the card the way libdrm does, checks the core ioctls and master rules, objects and properties, makes dumb buffers and draws through `mmap`, sets a mode, flips four times with events (through epoll), makes atomic commits (a failing test, a mode change refused without `ALLOW_MODESET` and done with it, a nonblocking flip with its event), waits for vblanks, moves and hides the cursor plane (or sees `ENXIO` without one), exports a dma-buf, maps it, passes it to another process over a socket and imports it there, reads the primary plane's `IN_FORMATS` and makes a framebuffer with the linear modifier (`GETFB2` reports it; `MOD_INVALID` is refused), checks error paths, and checks that the desktop comes back when it closes the card and when a child holding the display is killed. While it shows red, green, blue and white quadrants, and again after the kill, it writes `harness: screendump NAME` to `/dev/kmsg`; `xtask` takes a QEMU screendump (QMP) and checks the quadrants and the stand-in desktop's colour (`check_screendumps`).
- `cargo xtask test`, the `modetest` kernel test: libdrm 2.4.114's own `modetest`, built unmodified with the library, static with musl (`xtask/src/libdrm.rs`, into `/System/Linux/bin/modetest`), opens the card by driver name (`-M`), lists everything, sets a mode and page-flips on every event for 6 seconds (`-s … -v`, ending when its input does), then runs its atomic loop (`-a -s … -P … -v`, blocking commits at the refresh rate) until it is killed, after which the desktop must have the display back. It reports about 60 flips per second on every device.
- `cargo xtask test --mesa [--gpu std|virtio]`: the Mesa tests alone (filter `Mesa`), on a disk with Debian's Mesa, kmscube, glmark2's DRM and Wayland builds, `mesa-utils-bin`, `vulkan-tools` and `vkcheck` (`target/mesa-root`, about 110 packages and 345 MiB, fetched once; `xtask/src/mesa.rs`) and 2 GiB of memory. kmscube draws 240 frames full screen and the harness checks a screendump taken while it runs (grey corners, a coloured cube in the middle); `glmark2-drm` (desktop OpenGL 4.5) and `glmark2-es2-drm` run their `build` and `texture` scenes full screen and report a score, with screendumps showing their picture instead of the desktop's; `vulkaninfo` must list lavapipe and `vkcheck` (`linux-programs/vkcheck`: a graphics pipeline with hand-written SPIR-V shaders) draws a red triangle on blue and checks pixels it reads back; `es2gears` runs through `wl-bridge` and its window must show the red gear turning (30 different pictures) from dma-bufs. With the compositor running (`linux_mesa_composited`): es2gears' window composited from its dma-bufs (a screendump checked against the compositor's picture) and es2gears killed mid-frame (its window goes, the bridge stays); then `glmark2-es2-wayland --fullscreen --visual-config a=0`, scanned out directly (a screendump checked against the buffer on the plane), back to compositing for a notice (screendump checked against the compositor's picture), for Shoal and, without a cursor plane, for the pointer shown again, and to scanning out after each; glmark2 killed while scanned out, after which the plane shows the desktop's picture again.
- `cargo xtask test` (any `--gpu`), the `drmtest` test also checks a dma-buf's fences (`poll`, `EXPORT_SYNC_FILE`, the sync file's `FILE_INFO` and `MERGE`, `IMPORT_SYNC_FILE`) and a window showing a dma-buf and then shared memory as they are (`win_buffer`, `win_attach`, the `BUFFER_RELEASE` of the one replaced, the errors). After each full-screen program the desktop must have the display back. Both boots take about four minutes under TCG (the whole default suite about three). It is opt-in rather than part of `cargo xtask test` because of what it needs, not its time: the packages from the network (the default suite runs offline), a 600 MiB disk made afresh for each run instead of 128 MiB, and 2 GiB of memory instead of the 512 MiB the default suite's memory-exhaustion and fuzzing tests are sized for.
- `cargo xtask test --gpu virtio --displays N` (2–4): the `displays: …` kernel test runs the compositor on N scanouts. The harness plugs the extra heads in and out like a VNC viewer resizing its window (`SetDesktopSize`, 0×0 unplugs; `xtask/src/testdisplays.rs`) and checks what each head shows with QMP `screendump`s against the compositor's back buffers. It covers the layout, a new window opening on the pointer's display, the pointer crossing and stopping at an edge, damage presented only on its display, a display slowed to 300 ms per present not holding up the others, a window leaving an unplugged display and coming back, arranging, changing the main display and mirroring through preferences, the arrangement restored by identity on the second boot, and the frame cost with 3, 2 and 1 displays. With one display (any `--gpu`) it runs the single-display part.
- `tools/vnc.py` (with `AURORA_QEMU_ARGS="-vnc unix:$PWD/target/vnc.sock"`): the cursor image and hot spot the host received, and `resize:W,H` to resize the "host window" as a VNC viewer does.
